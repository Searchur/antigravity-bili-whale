# 长期状态契约

本文描述长期状态的存储边界、提交与恢复约定。

## 1. 权威与目录隔离

- 长期状态按 `account + owner` 的指纹隔离，目录为 `%USERPROFILE%\.antigravity-bili-whale\memory\<fingerprint>\`（可通过 `BILI_WHALE_HOME` 覆写），不与其他客户端共用目录。
- `checkpoint.json` 是已提交状态的权威检查点，包含身份、schema、状态摘要和完整状态。
- `state.json` 是兼容投影，不得覆盖权威检查点。
- 已建立检查点后，如果检查点缺失、摘要错误、身份不符或投影 revision 超前，读写必须 fail-closed；不得自动重置或退回旧投影。
- 缺少投影但检查点完整时，可以直接从检查点恢复。
- `checkpoint.json` 提交成功后，即使投影写入失败，已提交结果仍然有效；调用方可以收到错误，但重启后不得重复平台副作用。

## 2. 模块职责

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `src/life/persistence.mjs` | 初始状态、检查点权威、投影兼容读取（原子写委托给 `src/core/atomic-json.mjs`） | 子系统字段校验、事务业务规则 |
| `src/life/store.mjs` | 进程锁、事务边界、revision、提交顺序、公共 facade | 独立拥有归档算法或第二套检查点逻辑 |
| `src/life/archive.mjs` | 热事件压缩、引用保护、冷归档、过期删除（只读校验由 `src/memory/archive-reader.mjs` 承担） | 推进检查点、执行网络或模型任务 |
| `src/memory/cognition.mjs` | 经历序号、归纳作业、游标、候选与提交规则 | 直接写 checkpoint 文件 |
| `src/memory/dynamic-memory.mjs` | 场景化召回、读取预算、使用记录与记忆生命周期 | 绕过可见性和版本检查 |
| `src/affect/state.mjs` / `src/daemon/affect-worker.mjs` | 心情、话题、主人私信后续追问与主动表达结算 | 绕过 guarded CLI 直接发送 |

所有子系统仍在同一事务中提交；模块分离不代表可以把状态拆成多个互不一致的权威文件。

## 3. 状态所有权

| 状态 | 主要写者 | 主要读者 | 关键约束 |
| --- | --- | --- | --- |
| `events` | 受信事件入口、发送结算、调度记录 | 归纳、检索、归档 | 来源必须可核对；重复键不得重复写入 |
| `memories` | 动态记忆归纳提交 | 场景 reader、上下文编译 | 修正使用 base ID 与版本；失效记忆不得作为当前理解召回 |
| `proposals` | 兼容保留（旧检查点） | 状态校验 | 兼容保留空数组或历史记录，新版本控制台不再使用人工逐条审批 |
| `cognition.jobs` | formation worker | 调度器、状态工具 | 两阶段提交；租约、权限版本、来源摘要必须仍有效 |
| `cognition.cursor` | 归纳提交 | 后续批次与归档 | 只能随已确认消费推进，失败或缩批不得跳过未选经历 |
| `drafts` | 兼容保留（旧检查点） | schema 校验 | 兼容保留旧版数组结构，新版本直接由模型编写正文并经两段式发送与安全审核发送 |
| `pending` | reserve / dispatch / settle | 发送检查、恢复工具 | 未确认写入阻塞同目标重发；只有明确回执或人工核查可解除 |
| `threads` | 评论结算与线程管理 | 回复检查 | 冷却、预算、已处理坐标和恢复许可必须保留 |
| `leases` / `agenda` | 兼容保留（旧检查点） | schema 校验 | 兼容保留旧版数组结构 |
| `archives` | 归档模块 | 冷检索、导出、校验 | 文件摘要不符即失败；不得读取路径表以外的任意路径 |

## 4. 提交与恢复顺序

一次事务按以下顺序运行：

1. 获取跨进程锁并读取权威状态。
2. 执行兼容升级和状态准备。
3. 运行业务回调，同步并校验相关子状态。
4. 执行引用感知归档。
5. 若状态没有变化，只在需要时修复缺失或落后的投影，不增加 revision。
6. 若状态发生变化，先增加 revision 并原子提交 checkpoint，再写兼容投影。
7. 提交完成后调用 `afterCommit`，随后由 `finally` 释放锁。回调开始执行时锁尚未释放；异步回调的剩余执行可能与锁释放交错。

恢复时不得重放网络请求。`replayCheck()` 只验证检查点与归档，不产生平台副作用。

## 5. 归档与遗忘不变量

- 活跃记忆和在途归纳作业引用的来源必须保留。
- 近期未处理经历保留有界热窗口；较早溢出可以进入冷归档。
- 已过期且不再被引用的普通事件可以真正删除，而不是无限移入归档。
- 未确认发送、线程关闭状态及仍具去重价值的近期回执不得因压缩而丢失。
- 已完成管理历史可有界转入冷存储；检索和导出必须验证归档摘要。

## 6. 版本与迁移

当前顶层状态仍为 `version: 1`，checkpoint 使用 `schema: 1`。既有升级分支继续保持原行为。

后续若改变持久化结构，应新增显式、顺序、可重复执行的迁移，而不是在业务事务中继续叠加隐式升级条件。迁移至少需要：

- 原状态备份与身份检查；
- 从上一公开版本和近期 memory 版本升级的夹具；
- 中断后的重入测试；
- 失败时不覆盖最后有效检查点；
- 明确哪些旧字段只读、何时停止兼容。

## 7. 验证边界

自动化测试覆盖状态机、故障注入和模拟宿主，不等于真实模型质量或真实平台投递验收。真实 Antigravity App、内置模型、长期自然运行和平台回执仍需独立验证；测试中的模拟回执不得解释为实际发送成功。

旧版检查点中已提交的历史记录继续按原可见范围检索和导出，达到热事件保留上限后统一按规则进入冷归档。
